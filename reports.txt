5. Two things that must change before the abstract
--------------------------------------------------

5.1 The "~2x floor vs UNIX socket at large payload" claim in README.md does
    not hold on bare metal.

    Measured floor is 1.1x - 1.5x, not 2x, and it is non-monotonic:
    1.10x at 256 KiB, rising back to 1.47x at 1 MiB. This is real
    bare-metal data superseding the VM-derived indicative table, so the
    README claim needs revising DOWN, not the reverse. Better to walk in
    with 1.5x and be right than 2x and get caught.

5.2 p99.9 is currently unusable for the abstract.

    Spread across reps is enormous — zcring at 64 B ranges from 997 ns to
    1.18 ms across 5 reps at the SAME config. All three transports show
    this, so it is not a ring defect; it is OS scheduling noise on a
    non-isolated, non-RT kernel. This is exactly the gap PLAN.md section 5
    flags (isolcpus / nohz_full / PREEMPT_RT — item 4 in CONTEXT.md's
    next-tasks list). Do not quote p99.9 until that work is done.

8. What was built
-----------------

One producer, N consumers, every consumer sees every message, zero copies
for all of them. Full design rationale is in the header block of
src/zcring.h; the three decisions, as required:

8.1 Per-consumer cursors, min-cursor gating.
    Each consumer owns a cursor on its own cache line. The producer may
    recycle a slot only once the slowest ACTIVE consumer has passed it.
    Rejected the alternative (per-slot refcounting) because it places a
    contended atomic RMW on a line shared by all N consumers, degrading
    fan-out exactly where it should scale, and because it has no answer for
    a consumer that dies holding a reference — the count never reaches zero
    and the slot leaks permanently.
    The O(N) minimum scan is kept off the fast path by a cached gate. The
    cache can only ever be stale-low, which is the conservative direction,
    so acting on it is always safe.

8.2 Slow consumer -> backpressure, not drop.
    zc_bcast_reserve() returns NULL rather than overwriting. Reasons, in
    priority order: (a) it keeps "every active consumer receives every
    message" a checkable invariant — under a drop policy a message lost to
    a slow consumer is indistinguishable from one lost to a memory-ordering
    bug; (b) drop policy belongs to the application, which is the only layer
    that knows whether a stale frame is better discarded or delivered late,
    so the depth is exposed via zc_bcast_lag() instead; (c) the usual
    objection to backpressure is a liveness problem, answered in 8.3 rather
    than by discarding data.
    Stated cost: the slowest consumer paces everyone. A source that cannot
    be paced must size the ring for worst-case stall or implement
    drop-oldest on top of zc_bcast_lag().

8.3 Join, departure, death.
    Join is a three-state FREE -> CLAIMED -> ACTIVE handshake. A single CAS
    to ACTIVE would expose a stale cursor from the entry's previous occupant
    and stall the producer; CLAIMED entries are skipped by the gate, giving
    the joiner a window to install a cursor. Consumers join at the current
    head, not zero.
    Clean departure stores FREE; the gate skips it immediately. No slot is
    leaked because consumers never own slots, only cursors.
    Death without leaving is the deadlock risk. zc_bcast_reap() walks ACTIVE
    entries and evicts any whose owning process is gone. Off the fast path
    (one syscall per entry). It evicts the dead and never the merely slow —
    a descheduled consumer is alive and keeps its backpressure, which is
    what 8.2 argues for.
    Two limitations documented rather than hidden: it is process-granular
    (a dead thread inside a live process is invisible), and a zombie is
    still a process (the parent must wait() before the cursor is
    reclaimable).

ABI version bumped 1 -> 2; zc_attach() rejects a mismatch rather than
misreading offsets. Mode is fixed at creation so unicast and broadcast
cannot be mixed on one ring.

The fan-out test runs against a deliberately undersized ring (16 slots,

strictly stronger invariant than Layer 1's exactly-once across the consumer
set, and is only checkable because the policy is backpressure rather than
drop.

Note on TSan coverage: TSan cannot see across process boundaries, so the
cross-process tests give it nothing. The thread-based fan-out test is what
actually exercises the new shared state under the sanitiser.


10. Two measurement bugs found and fixed
----------------------------------------

Both would have produced misleading numbers had they gone unnoticed.

10.1 Consumer pinned to the producer's SMT sibling.
     The first implementation round-robined consumers over online CPUs,
     which placed one on cpu0 — the SMT sibling of the producer's cpu2.
     p50 was unaffected; p99 was inflated 185x (1.2 ms vs 6.6 us).
     --cpu-cons now takes an explicit list and scripts/fanout.sh derives it
     from thread_siblings_list. On this 2-physical-core box that means one
     hyperthread is deliberately left idle.

10.2 Spinner oversubscription at N=4.
     zcring waiters busy-wait while pipe/unix block in read(). At N=4 that
     is 5 spinning threads on 4 hardware threads, and the benchmark measures
     scheduler thrash rather than fan-out: p50 90 us at 4 KiB, against
     2.1 us with bounded-spin-then-yield. A 40x artifact.
     Added --yield and used it for the whole sweep. Measured cost at N=1 is
     ~8%, so it is the conservative choice, not a flattering one. It is a
     no-op for pipe/unix, which already block. The real fix is adaptive
     spin-then-futex notification, which is now the next work item.

12. The 1 MiB N=4 cell is an overload artifact, not a transport result
---------------------------------------------------------------------

At gap=100us the offered load is ~10 GB/s produced and ~42 GB/s of consumer
reads (4 consumers x 1 MiB x 10k msg/s), which is far beyond this machine's
memory bandwidth. The system is saturated, so the number measures queueing
delay, not transport cost.

The two transports then behave differently for a structural reason worth
understanding rather than hiding:

  - zcring's ring at 1 MiB is 64 slots = 64 MiB of buffer. It absorbs the
    overload as queueing delay, so latency climbs without bound.
  - A UNIX socket has a ~200 KB buffer. It throttles the producer at the
    source almost immediately, so its *latency* stays bounded while its
    throughput silently drops.

This is classic bufferbloat: a deep buffer converts overload into latency, a
shallow one converts it into backpressure. Comparing them at a saturating
offered rate is not a like-for-like measurement.

Confirmed by varying the offered rate at 1 MiB, N=4:

    gap=100us   p50 = 8.78 ms      (saturated)
    gap=500us   p50 = 128 us       (68x collapse)
    gap=2000us  p50 = 137 us
    gap=5000us  p50 = 138 us

Below saturation the fan-out story is clean and monotonic
(results/fanout_1mib_unsaturated.csv, gap=2000us, 5 reps):

    1 MiB     zcring     pipe     unix    ratio
    ------------------------------------------------
    N=1      107.8us  346.6us  250.0us    2.32x
    N=2      131.7us  613.9us  331.1us    2.51x
    N=4      145.1us  940.2us  507.9us    3.50x


13. The headline result — latency growth with consumer count
------------------------------------------------------------

This is the scalability claim, and it is the graph to build. p50 growth from
N=1 to N=4 (lower is better scaling):

    size       zcring    pipe    unix
    -------------------------------------
    16 KiB       1.4x    1.8x    1.8x
    64 KiB       1.2x    1.9x    2.1x
    256 KiB      1.1x    2.7x    2.6x
    1 MiB *      1.3x    2.7x    2.0x     (* unsaturated run)

At payloads where copying dominates, zcring latency is close to flat in the
consumer count while both comparators grow roughly linearly. That is the
copies-avoided argument showing up directly in measurement: publication is
one release store regardless of N, whereas pipe and unix each pay N copies
in and N copies out.

Consequently the advantage widens with N exactly where the single-consumer
baseline was weakest:

    256 KiB:  1.09x (N=1) -> 1.78x (N=2) -> 2.47x (N=4)
    1 MiB:    2.32x (N=1) -> 2.51x (N=2) -> 3.50x (N=4, unsaturated)

This is the direct answer to the weak large-payload column in the Layer 1
baseline. The single-consumer 1.1-1.5x was never the interesting case; the
framework's advantage is multiplicative in the number of consumers, and that
is what the rubric's *scalability* criterion is asking for.

Caveat to state before a judge finds it: small payloads show the opposite
growth pattern (zcring 4.3-10.4x from N=1 to N=4 versus 2.3-2.9x for the
comparators). That is not a copy-cost effect — it is dividing by a ~120 ns
baseline. In absolute terms zcring is still 5.1x faster than the best
comparator at 64 B with N=4. The growth ratio is the wrong metric when the
denominator is a hundred nanoseconds; quote the absolute latency there.


14. Hard limit of this hardware
-------------------------------

Fan-out scalability cannot be demonstrated credibly past N~2 on this
machine. Two physical cores means N=4 oversubscribes regardless of
implementation quality, and one hyperthread is already sacrificed to keep
the producer's core clean. The N=1 -> N=2 -> N=4 *trend* is real and
defensible; the N=4 absolute numbers are a property of the measurement box
and must be presented as such.

If a stronger scalability claim is wanted, it needs a machine with more
physical cores — and per CONTEXT.md the WSL2 Ryzen is not a valid measurement
platform, so that would mean new hardware, not the existing dev box.


15. New finding: deep C-states are polluting the tails
------------------------------------------------------

The p99.9 data contains a pattern that is backwards on its face: at 64 B,
zcring p99.9 is 1220 us at N=1 but 2.9 us at N=2 and 8.0 us at N=4. More
consumers cannot genuinely improve tail latency.

Cause is CPU idle states. This machine exposes:

    state0  POLL      exit latency     0 us
    state1  C1_ACPI   exit latency     1 us
    state2  C2_ACPI   exit latency   253 us
    state3  C3_ACPI   exit latency  1048 us

C3's 1048 us exit latency matches the observed 1220 us p99.9 almost exactly.
At N=1 with --yield, the consumer is idle ~99.9% of the time between 100 us
messages, so its core drops into C3 and occasionally pays the full exit
latency. At N=2 and N=4 the cores stay busy, never reach C3, and the tail
collapses to single-digit microseconds.

Not yet confirmed by experiment — `cpupower idle-set -D 0` needs root and
the sudo credential had expired. The confirming run is:

    sudo cpupower idle-set -D 0
    ./build/bench --transport=zcring --consumers=1 --size=64 \
                  --count=20000 --gap-us=100 --touch --yield \
                  --cpu-prod=2 --cpu-cons=3,1 --csv

Expected: p99.9 drops from ~1.2 ms to single-digit microseconds.

This matters beyond fan-out. Item 4 in the task list (determinism rigor,
p99/p99.9 histograms, isolcpus / nohz_full / PREEMPT_RT) is described as the
top differentiator, and idle-state exit latency is a first-order contributor
to tail latency on any embedded-class part. Disabling deep C-states belongs
in the quieting checklist alongside the governor setting, and the C-state
table above is itself good material for the determinism section: it is a
concrete, measurable, hardware-level source of jitter with a documented fix.

p99.9 remains not quotable pending that work.

25. New session: camera fan-out demo (make demo)
--------------------------------------------------------------------------

Requested: a live demo pipeline -- camera producer, three consumers doing

Design decisions made before writing code:

- All three consumers touch every pixel, not just the ones whose logical
  job would require it. A jitter-tracker realistically only needs the
  8-byte timestamp header; deliberately not doing that, because a consumer
  that conveniently ignores most of the frame would make zcring's win look
  bigger than the transport actually earns, and this project's whole
  --touch discipline exists to prevent exactly that shortcut. jitter got a
  full-frame min/max scan bolted on for this reason.
- Frame drops use a real per-tick sequence counter (frame_seq, incremented
  every 30fps tick whether or not that tick got published), so gap
  detection works identically on both transports without needing
  transport-specific bookkeeping.
- Drop policy: a camera cannot be paused, so the producer never blocks
  indefinitely. zc_bcast_reserve() gets ~1.5 frame periods of bounded
  retry before the tick is skipped; the socket path uses poll() with the
  same bound on all three sockets before committing to write(), skipping
  the tick for all three if any isn't ready -- keeping "which frames every
  consumer saw" identical between transports rather than letting sockets
  drop independently per-consumer.
- "Memory traffic avoided" reuses the exact accounting already defended in
  README's benchmark methodology section (1 producer write + N consumer
  reads for zcring; 1 staging write + N*(kernel-in + kernel-out + consumer
  read) for sockets -- 2*N passes avoided per frame), not a new formula
  invented for this demo.

CPU pinning: producer + 3 consumers is 4 roles, and this machine has
exactly 4 logical CPUs on 2 physical cores. Every role gets a distinct
logical CPU, but one consumer (checksum, cpu0) necessarily shares a
physical core with the producer (cpu2) -- same hardware ceiling as N=4
fan-out (STATUS.md Open problem #3), just arrived at by a different route.

Two real bugs found by testing failure modes directly, not by inspection:

1. Piped the demo through `head -40` to look at early output. The pipe
   closing early killed the producer via SIGPIPE (default disposition:
   terminate), and the three forked consumers -- now orphaned -- kept
   spinning at ~98% CPU indefinitely, confirmed via `ps`. Root cause:
   g_stop is a per-process flag; a producer that exits via signal never
   gets to tell its children. Two-part fix: SIGPIPE now ignored in the
   producer (a closed stdout shouldn't kill a 10-minute run over a
   redirect), and every producer exit path (natural duration, Ctrl-C,
   anything else) now explicitly SIGTERMs all three consumers rather than
   relying on them noticing on their own.

2. That fix isn't enough for SIGKILL, which no handler can catch. Tested
   this directly: backgrounded the producer, waited 3s, `kill -9`'d it,
   watched the children. First fix attempt used `getppid() == 1` as an
   orphan watchdog (checked once per sched_yield() in the consumer's spin
   loop) -- standard Unix idiom, and it did NOT work. `ps -o ppid` on the
   orphaned children showed PPID 3506, not 1: this environment (this
   sandbox) reparents orphans to a subreaper, not init, so `== 1` never
   fires here. Fixed by capturing the parent's PID immediately after
   fork() and checking `getppid() != orig_parent` instead -- correct

26. Layer 2 adaptive notification: online-learned spin-then-futex threshold,
    and the busy-spin hypothesis refuted for good
--------------------------------------------------------------------------

Built the last unstarted piece of Layer 2: adaptive notification. Removed the
fixed YIELD_SPINS constant and the --yield stopgap entirely; --notify
replaces both. Full design rationale is in src/zcring.h SS5-SS10 and is
written to be read by a judge, not just by a maintainer -- this is the
project's answer to HACKATHON.md's AI/Technical Approach criterion, which is
a CORE scored criterion the project previously scored zero on.

What the policy actually is (short form; the header has the derivation):

  objective    minimise expected added latency W*(1-F(S)) subject to expected
               spin cost E[min(X,S)] <= beta*E[X]. beta -- the fraction of an
               idle gap you'll burn spinning -- is the ONLY policy input.
               Everything else is measured. That split is the argument.
  estimator    multiplicative Robbins-Monro quantile update,
               S <- S + eta*(p - 1[X<S]) with eta = gamma*S, done as two
               shifts and an add. Scale-free (crosses decades of message rate
               without retuning) and deliberately non-annealing (an arrival
               process that changes is one you must keep listening to).
               Target quantile is set by the ratio of the two shifts:
               p = 2^DOWN/(2^DOWN+2^UP) = 16/17 at the defaults.
  budget       enforced against MEASURED E[min(X,S)] (an EWMA of actual spin
               burned), not against the bound E[min(X,S)] <= S. beta is a
               shift, so the whole update is division-free.
  wake cost W  measured, not assumed. The producer stamps CLOCK_MONOTONIC
               into ctrl->wake_ts immediately before FUTEX_WAKE. Double duty:
               it measures what sleeping cost, AND it de-censors the arrival
               sample -- without it every blocked wait reports X+W instead of
               X, so the estimator gets pushed toward spinning by exactly the
               outcome that should not do that.
  floor        ski-rental: S >= measured W, always. 2-competitive and
               distribution-free. Makes fast-arrival traffic stay
               syscall-free automatically (gap << W => floor dominates =>
               never blocks) and slow-arrival traffic block on nearly every
               message (gap >> W => budget dominates). A fixed constant
               cannot have both behaviours; that is the whole point.
  exploration  eps-greedy, eps=1/128, explore at 8x budget. NOT decoration:
               the greedy policy censors its own observations and cannot
               distinguish "6% of gaps land just past S" (raise S, nearly
               free) from "6% of gaps are 100x S" (raising S is pure waste).
               Extra cost bounded by eps*(m-1)*S < 6% of S, and charged
               against the same budget so it can't smuggle in unauthorised
               spend.

ABI: unchanged, still v2. wake_ts fits inside padding _Alignas had already
reserved in the futex_word cache line (offsets 200-255 were free), and the
notify flag rides in spare high bits of ctrl->mode. Added _Static_asserts on
sizeof(zc_ctrl_t) and six field offsets so this is enforced rather than
claimed -- confirmed byte-identical to the pre-change build (1344 bytes;
head=64 tail=128 futex_word=192 waiters=196 wake_ts=200 gate_cache=256
cons=320).

Two implementation decisions worth recording because both were changes of
direction mid-build:

(a) The wake protocol was written first with atomic_thread_fence(seq_cst) on
    both sides -- the canonical store-buffer fix, what Folly's EventCount and
    glibc's condvar do, and correct. Rewrote it because `make tsan` emitted
    -Wtsan: GCC's ThreadSanitizer does NOT model atomic_thread_fence, it
    warns and skips. That would have left the single most delicate ordering
    in the framework as the one thing tsan cannot check -- unacceptable given
    this project's own stated rule about tsan. Replacement uses a seq_cst
    read-modify-write on the SAME word from both sides: the consumer does
    fetch_add(&waiters, 1), the producer does fetch_add(&waiters, 0) purely
    to read it. RMWs on one object are totally ordered by that object's
    modification order and each reads the immediately preceding value, so
    there are exactly two cases and both are safe (producer sees >=1 and
    wakes; or the consumer's RMW reads-from the producer's release RMW,
    synchronizes-with it, and therefore sees the message and does not sleep).
    No fence, TSan models it exactly, and on x86 it costs one uncontended
    LOCK XADD against an MFENCE. Strictly better on every axis that mattered.

(b) zc_wake() started as a static inline in the header and was moved out of
    line into zcring.c. Reading the generated assembly showed that inlining
    it pulled zc_now_ns()'s struct timespec into the caller's frame, which
    under -fstack-protector-strong (Ubuntu/Debian default) added canary setup
    and teardown to EVERY zc_commit -- including on rings with notification
    disabled. That would have quietly invalidated the claim that the
    non-notify fast path is unchanged, and with it the reproducibility of
    every committed dataset. After the move, plain zc_commit is: mask, store
    len, release-store seq, load local r->notify, test, branch, ret. Verified
    in the assembly, not assumed.

Tests: four new notification tests plus a dedicated lost-wakeup stress test
that aims at the arm/publish boundary (publish gap swept across 2-14.4us so
the collision is hit from both sides rather than at one fixed offset the
policy could settle away from), using a bounded wait so a lost wakeup
surfaces as a counted timeout instead of a hung CI run. Also asserts the
policy actually SLEEPS (>50% of waits block at a 200us gap) and actually
does NOT sleep when arrivals are fast (<5% of 20000), since a policy that
silently degenerated to spinning would pass every delivery check while
delivering none of the point. make test and make tsan both clean, no
warnings in either build.

Convergence, from bench --notify's reported state (64 B, N=1, gap=100us):

    spin=11904ns gap_ewma=97782ns wake_ewma=2068ns burn_ewma=12196ns
    waits=20766 blocks=20667 (99.5%) explores=170

gap_ewma recovered the true 100us inter-arrival; spin settled at gap_ewma/8,
i.e. the CPU budget binding exactly as derived; wake cost measured at ~2us;
explore rate 0.82% against a nominal 1/128 = 0.78%. At 1 MiB the same
estimator learned a 185us gap -- the REAL inter-arrival, not the 100us
nominal pacing, because the producer's own 1 MiB write pass slows it down.
That is the difference between measuring and configuring, and it is worth
showing a judge directly.

Honest cost, stated rather than buried: at 64 B / 100us gap, p50 goes from
~128ns (spin) to ~2.2us (notify), because nearly every message now pays a
wake. sweep.sh therefore still defaults to WAITER=spin, which keeps
results/sweep.csv reproducible; WAITER=notify produces the blocking variant.
The two answer different questions (lowest achievable latency given a
dedicated core, vs latency at an idle CPU cost comparable to a socket) and
must never be blended into one table.

    spin              118.4us   194.0us   +63.9%
    notify            122.2us   197.5us   +61.6%
    unix (control)    157.4us   174.0us   +10.5%

NEGATIVE RESULT, and this time a conclusive one. With C-states disabled,
zcring costs the same whether the consumer spins or genuinely sleeps: 194.0
vs 197.5 at gap=100, 180.5 vs 184.1 at gap=2000. The waiter is not the
mechanism. The hypothesis predicted a real block/wake cycle would recover
something near the C-states-enabled figure; it recovered nothing.

The -6.6% must not be misread as the penalty shrinking. It is the
C-states-ENABLED baseline getting worse under notify, and that is a second,
separate, fully-explained finding: at a 2ms idle gap a blocking consumer's
core has time to enter a deep C-state, so its wake pays that state's exit
latency -- ~91us here (notify+C-on 197.1 vs spin+C-on 106.1). The same
mechanism hits the control, which is how we know it is the mechanism: unix
is 36.7% FASTER with C-states disabled at this rate.

That corrects a claim this repo has been making since item 22: "pipe/unix
are not affected by the C-state setting". True at gap=100us, where the idle
window is too short for the governor to pick a deep state. False at
gap=2000us. It was a rate-specific observation reported as a general one.
README.md is fixed; treat any older statement of it as superseded. It also
strengthens rather than weakens the determinism argument -- disabling deep
C-states is a requirement for ANY blocking transport's tail, not a zcring
quirk.

Running tally on the ~65-70% zcring pays at 1 MiB with C-states disabled:
eliminated as causes are offered rate (item 21), thermal throttling in
isolation (item 19), and now busy-spin (this item, conclusively). What
remains are platform properties rather than properties of this code --
uncore/memory-controller frequency, or a turbo/RAPL budget a
never-fully-idle package cannot reach. Not worth more time before the
deadline. It is disclosed either way, and the fan-out crossover is what wins
the large-payload case back regardless of mechanism.

29. Huge-page backing for the arena: built, with the A/B still owed --
    and one negative result already banked
--------------------------------------------------------------------------

Item 27 closed the list of *code* explanations for the ~65-70% zcring pays
at 1 MiB with C-states disabled, and named what was left as "platform
properties". One candidate on that list is cheap to test and is not
really a platform property at all: address translation.

The arithmetic. At a 1 MiB payload with 4 KiB pages, one message spans 256
pages. The producer walks 256 PTEs writing it; the consumer walks 256 more
reading it, in a different address space with its own TLB entries for the
same physical pages. The L1 dTLB on this part holds ~64 entries, so every
message misses it comprehensively, twice, and the second-level TLB and page
walker absorb the rest. A 2 MiB page makes the same message one PTE per
side. If translation is a material part of the gap, forcing huge pages has
to move the number.

What was built (src/zcring.h §11, src/zcring.c):

  - ZC_HUGE_AUTO, the default: try MFD_HUGETLB on the memfd; if that fails,
    a normal memfd with the arena madvise(MADV_HUGEPAGE)'d; if that fails,
    4 KiB pages. Fallback is silent and unconditional by design. Embedded
    kernels routinely ship without hugetlbfs, and an IPC framework that
    refuses to start there has traded its entire target platform for a TLB
    optimisation.
  - ZC_HUGE_OFF reproduces the pre-§11 layout byte for byte, which is what
    keeps everything in results/ regenerable.
  - ZC_HUGE_REQUIRE fails creation rather than falling back. It exists for
    benchmark arms: an arm that quietly gets 4 KiB pages measures the
    control twice and reports a null result as a confirmed one.
  - The arena's FILE OFFSET is aligned to the huge-page boundary, and the
    mapping is placed at a huge-aligned VIRTUAL address (PROT_NONE
    reservation, then MAP_FIXED into the aligned middle, then the slack
    unmapped -- in that order, so no window exists where another thread's
    mmap could take the address). Both are required: mmap(NULL) gives page
    alignment and nothing more, and THP will not use a PMD for a region
    that does not start on a 2 MiB boundary. Getting only one of the two
    right yields a madvise that succeeds and does nothing.
  - The control block and slot array live in the first huge page and are
    deliberately NOT advised. They are a few cache lines that want to stay
    where they are, not 2 MiB of hot TLB entry.
  - AUTO attempts huge backing only when the arena is >= 4 huge pages
    (ZC_HUGE_MIN_PAGES). A 64 KiB arena rounded up to 2 MiB would consume
    32x its size from a scarce global pool to save TLB misses it was never
    taking. In practice this means the mechanism only ever engages at large
    payloads -- which is the only regime it was hypothesised to help.

ABI is UNCHANGED at v2. Both flags (F_HUGETLB, F_HUGEALIGN) ride in spare
high bits of ctrl->mode, the same trick §9 used for notification, so
zc_ctrl_t is byte-for-byte identical and the six _Static_asserts on its
layout still pass untouched.

One real bug found while writing it, worth recording because it would have
been invisible until the pool ran dry mid-sweep: zc_attach() peeked the
control block with mmap(sizeof(zc_ctrl_t)) and munmap'd the same length. On
a hugetlbfs-backed fd the kernel rounds a mapping's length up to the huge
page size, so that maps 2 MiB and the 1344-byte munmap fails with EINVAL --
leaking a huge page of a global pool on every single attach. Replaced with
pread(), which has no such rule and costs one fewer syscall besides.

NEGATIVE RESULT, already conclusive: the THP fallback is a dead end on this
machine, and reporting it as if it were huge pages would have been the easy
mistake to make.

    $ cat /sys/kernel/mm/transparent_hugepage/shmem_enabled
    always within_size advise [never] deny force

Transparent huge pages for SHARED memory are gated on their own knob, and it
ships as `never` on stock Ubuntu. The madvise still returns 0. VM_HUGEPAGE
still appears in the mapping's VmFlags (`hg`). The arena is still 4 KiB
pages throughout. Probed directly -- created a ring under AUTO, faulted all
64 MiB of arena, then read that VMA's /proc/self/smaps entry:

    79fff7600000-79fffb600000 rw-s 00200000 00:01 652   /memfd:zcring
    Rss:               65536 kB
    ShmemPmdMapped:        0 kB
    THPeligible:           0
    VmFlags: rd wr sh mr mw me ms sd hg

VA 2 MiB aligned, arena_off 2 MiB aligned, advice accepted, zero huge pages.
The alignment machinery is provably correct and the kernel policy simply
declines. Hence the backing is reported as `thp-advise` and never as `thp`:
it is a request, not a receipt. Do not let a future session read that string
in a CSV and conclude an arm had huge pages.

NOT DONE: the 1 MiB N=1 A/B itself. It needs real 2 MiB pages, so it needs
hugetlbfs, whose pool is 0 by default and is set by a root sysctl this
machine's sudoers does not grant (only /usr/bin/cpupower is NOPASSWD). The
script is written, committed and ready -- scripts/hugepage_ab.sh, 4k vs huge
x zcring vs unix, 1 MiB, N=1, gap=100us, REPS=5, wait_for_cool() before
every invocation, C-states disabled, unix as the drift control. It records
the `pages=` line bench prints per row rather than the flag it passed, and
aborts if the huge arm did not get hugetlb. To run it:

    sudo sysctl -w vm.nr_hugepages=40    # 40 x 2 MiB = 80 MiB
    ./scripts/hugepage_ab.sh
    sudo sysctl -w vm.nr_hugepages=0     # give the memory back

The pool is deliberately not reserved by the script: it takes memory from
the rest of an 8 GB machine for as long as it is set.

The time-box stands as given. If huge pages do not move the 1 MiB number by
more than a few percent, record the negative result and stop -- the
remaining candidates (uncore/memory-controller frequency, turbo/RAPL budget
on a never-fully-idle package) are platform power properties, not properties
of this code, and are not worth more time before the deadline.

Two things guard the existing datasets while this is open. scripts/sweep.sh
and scripts/fanout.sh now pass --pages=4k explicitly, so neither dataset can
silently change meaning depending on whether vm.nr_hugepages happens to be
reserved on the machine at the time. And bench prints the backing it got to
