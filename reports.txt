0. Housekeeping / corrections
-----------------------------

- This machine is an i3-1115G4: 2 PHYSICAL CORES / 4 THREADS (SMT), not a
  true 4-core part as CLAUDE.md assumes. `nproc` reports 4, but `lscpu`
  shows "Core(s) per socket: 2". The sweep's pinning is still correct
  (cpu2/cpu3 map to distinct physical cores, verified via core_id), but the
  "4 cores, embedded-representative" framing in the abstract should say
  "dual-core w/ SMT", not quad-core.

- `git commit` needed a local identity; set to amitchowdary.d@gmail.com with
  a guessed name "Amit Chowdary". Fix if wrong.

- The root password pasted into the session transcript should be rotated.

- `make tsan` was genuinely broken on this kernel: ASLR/PIE base landing
  outside TSan's shadow-memory range, aborting before any test ran. Not a
  race in the ring. Fixed by wrapping the run in `setarch -R`; TSan now runs
  clean. Committed.

- `make clean` deletes results/ wholesale. Hit this by accident and restored
  from git. Worth knowing; the Makefile change itself is intentional.

5. Two things that must change before the abstract
--------------------------------------------------

5.1 The "~2x floor vs UNIX socket at large payload" claim in README.md does
    not hold on bare metal.

    Measured floor is 1.1x - 1.5x, not 2x, and it is non-monotonic:
    1.10x at 256 KiB, rising back to 1.47x at 1 MiB. This is real
    bare-metal data superseding the VM-derived indicative table, so the
    README claim needs revising DOWN, not the reverse. Better to walk in
    with 1.5x and be right than 2x and get caught.

5.2 p99.9 is currently unusable for the abstract.

    Spread across reps is enormous — zcring at 64 B ranges from 997 ns to
    1.18 ms across 5 reps at the SAME config. All three transports show
    this, so it is not a ring defect; it is OS scheduling noise on a
    non-isolated, non-RT kernel. This is exactly the gap PLAN.md section 5
    flags (isolcpus / nohz_full / PREEMPT_RT — item 4 in CLAUDE.md's
    next-tasks list). Do not quote p99.9 until that work is done.


6. Comparison against the WSL2 run
----------------------------------

Prior results/sweep.csv came from the 16-thread Ryzen under WSL2, and was
run WITHOUT --touch.

Comparator transports (pipe/unix), which are unaffected by the --touch
issue, confirm the hypervisor-jitter claim — and confirm it hits p50, not
just the tail:

    payload    transport   WSL2 p50     bare-metal p50   speedup
    ---------------------------------------------------------------
    1 KiB      pipe         22.81 us         2.27 us      10.1x
    1 KiB      unix         25.55 us         3.13 us       8.2x
    1 MiB      pipe        969.55 us       334.55 us       2.9x

The WSL2 zcring column is not comparable at all: that run predates
--touch and shows the harness artifact CLAUDE.md warns about — a flat
~90 ns p50 at every payload size including 1 MiB, which is not physically
possible. It is an artifact, not a measurement.
